# Модель безопасности

Human Gate создаёт задания CAPTCHA, проверяет ответы на сервере и ограничивает время и число попыток. После правильного ответа задание больше нельзя использовать. Приложение продолжает защищаемое действие только при результате `VerificationCode::Accepted`.

## Проверка ответа на сервере

При создании задания сервер выбирает его назначение через [`Purpose`](reference/api.md#основные-типы) и сохраняет данные, необходимые для проверки. Браузер получает идентификатор задания и сведения для его отображения, но не правильный ответ.

При отправке формы приложение передаёт идентификатор и ответ в [`ChallengeService::verify()`](reference/api.md#verify). Правильность ответа определяется по данным сервера. Идентификатор или содержимое запроса сами по себе не подтверждают прохождение CAPTCHA.

Пакет не хранит правильный ответ в открытом виде. Для [`CategorySelection`](challenges/category-selection.md) и [`IconSequence`](challenges/icon-sequence.md) браузеру передаются случайные токены вариантов без сведений о том, какие из них правильные. В первом задании порядок выбранных токенов не важен; во втором он определяет ответ.

## Срок действия и повторное использование

Срок действия задания и допустимое число неверных ответов настраиваются через [`Policy`](reference/api.md#policy). По умолчанию задание действительно 180 секунд и допускает три неверные попытки.

После принятого ответа тот же идентификатор нельзя использовать повторно. Если запись о задании ещё хранится, повторная проверка возвращает `AlreadyConsumed`. Когда старая запись удалена, результатом будет `NotFound`. Оба результата означают, что защищаемое действие по этому заданию выполнять нельзя.

Истёкшее задание также не может быть принято. Как работает обновление и когда старые идентификаторы перестают находиться, описано в [жизненном цикле проверки](reference/lifecycle.md).

## Хранение в сессии PHP

Поставляемый [`NativeSessionChallengeStore`](reference/api.md#хранилище-и-время) использует уже открытую приложением сессию PHP с обработчиком `files`. После изменения данных пакет закрывает сессию и проверяет, что изменение действительно сохранено. Если подтвердить запись нельзя, вместо успешного результата возникает исключение.

Приложение открывает сессию до обращения к библиотеке и самостоятельно управляет её дальнейшим использованием. Подробный порядок работы приведён в [руководстве по интеграции](guides/integration.md#хранение-в-сессии-php).

## За что отвечает приложение

CAPTCHA дополняет защиту приложения, но не определяет права пользователя. Приложение самостоятельно выполняет авторизацию, проверку CSRF, экранирование данных при выводе, ограничение частоты запросов и само защищаемое действие.

Если ограничение запросов зависит от IP-адреса, приложение также определяет адрес клиента. При работе через CDN или обратный прокси данные о клиентском IP из HTTP-заголовков можно использовать только от доверенных прокси. **Human Gate не определяет IP-адреса и не анализирует HTTP-заголовки**: его [`Policy::maxActive`](reference/api.md#policy) и `Policy::maxActivePerPurpose` ограничивают число сохраняемых заданий, а не частоту обращений.

Правильный ответ на CAPTCHA не заменяет прикладную транзакцию. Если после успешной проверки приложение выполняет отправку сообщения, запись в базу или другую операцию, её защиту от дублирования и обработку ошибок обеспечивает само приложение.

## Доступность и ограничения CAPTCHA

Текст и значки на изображениях могут распознаваться автоматизированными средствами. CAPTCHA не даёт гарантии защиты от любого бота и не заменяет другие меры безопасности.

Для пользователей, которым трудно или невозможно выполнить визуальное задание, приложение предусматривает [доступный альтернативный способ](accessibility.md) продолжить действие.
