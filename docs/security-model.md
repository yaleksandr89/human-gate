# Модель безопасности

## Граница доверия

Проверяйте CAPTCHA на сервере непосредственно перед защищаемым действием в том же запросе или потоке обработки приложения. Продолжайте действие только при `VerificationCode::Accepted`. Human Gate управляет проверкой задания; полномочия пользователя определяет приложение.

Данные браузера — входные и транспортные значения. Изображение, подписи, ID и токены не являются источником истины о правильности ответа. Сервер выбирает purpose и kind и использует состояние своего storage.

## Авторитетное состояние на сервере

Состояние проверки хранит серверные ID, purpose, kind, срок действия, число ошибок и proof ответа. Клиент получает данные из `IssuedChallenge` и `Presentation`, необходимые для показа задания и передачи ответа.

Proof и принадлежащая пакету область session остаются серверными. Приложение не отдаёт браузеру снимок состояния хранилища, канонические материалы proof или внутренние данные native session. Не записывайте эти данные в доступные клиенту ответы и журналы.

## Привязка challenge

Proof связан с challenge ID, purpose, kind и каноническим ответом. ID генерируется на сервере из безопасного источника случайности. `Purpose` задаёт логическое назначение действия и не принимается из браузера как авторитетное значение.

`verify()` разрешает kind из сохранённого состояния, а не из клиентского переключателя. `PurposeMismatch` — отказ; на его основании приложение не раскрывает внутреннее состояние чужого назначения. После удаления записи старый ID возвращает `NotFound`.

## AnswerProof

Открытый правильный ответ не хранится в авторитетном состоянии проверки. Поставляемые стратегии сохраняют SHA-256 digest, связанный с ID, purpose, kind и каноническим ответом, и сравнивают proof на сервере.

Это не шифрование ответа. Раскрытие proof позволяет перебирать короткий ответ без обращения к серверу, поэтому proof остаётся серверным. Не публикуйте его в JSON, HTML, изображениях с дополнительными метаданными или диагностике клиента.

## Одноразовая проверка и replay

Успешный `verify()` потребляет задание в том же атомарном переходе состояния и возвращает `Accepted`. Повтор при сохранённой терминальной записи возвращает `AlreadyConsumed`. После удаления записи старый ID возвращает `NotFound`; оба результата запрещают продолжение по старому заданию.

Срок действия и лимит неверных ответов ограничивают использование активного задания. Причины завершения хранятся ограниченное время и число записей; бессрочная диагностика старых ID не обещается. Точные условия — в [жизненном цикле](reference/lifecycle.md).

Отдельный протокол «решённого токена» не входит в v1. Приложение не заменяет непосредственную проверку бессрочным клиентским признаком прохождения CAPTCHA.

## Opaque tokens и данные клиента

CategorySelection и IconSequence используют случайные непрозрачные токены по 32 строчных hex-символа. Сервер не передаёт признак принадлежности карточки или варианта к цели, правильный набор токенов либо правильные позиции последовательности.

CategorySelection передаёт текстовое задание и подписи; порядок токенов ответа не важен. IconSequence передаёт изображения и требуемое число выборов; порядок токенов значим. Семантические названия значков и пути ресурсов не входят в его публичное представление.

Клиент переносит выбранные токены и показывает состояние выбора. Он не вычисляет правильность. Серверные proof и формат ответа описаны в руководствах [CategorySelection](challenges/category-selection.md) и [IconSequence](challenges/icon-sequence.md).

## Native PHP session storage

Поставляемый adapter работает в уже открытой приложением native files session с serializer `php` или `php_serialize`. Он строго проверяет ограниченное состояние пакета и не заменяет повреждённое существующее состояние пустым.

Реальное изменение фиксируется, session закрывается, затем сохранённая запись проверяется через повторное открытие только для чтения. Если фиксацию нельзя подтвердить, операция завершается исключением: успешный результат, включая `Accepted`, не возвращается. Это verified-commit поведение с отказом при неподтверждённой записи.

Receipt tokens и внутренние данные подтверждения storage остаются серверными. Их алгоритм не является интеграционным API. Гарантии применяются в поддерживаемой files-session среде; они не обещают распределённого консенсуса или транзакции с внешним действием приложения.

Начальное открытие session, порядок операций до заголовков и последующее сохранение `$_SESSION` описаны в [интеграции](guides/integration.md). Инфраструктурные причины `NativeSessionStorageException` перечислены в [API](reference/api.md); не передавайте их автоматически в браузер.

## Ответственность приложения

Приложение обеспечивает:

- HTTP-маршруты, контроллеры и проверку формы входных данных, включая предел входящего запроса.
- CSRF и авторизацию защищаемого действия.
- Экранирование текста и безопасный вывод изображений для выбранного контекста.
- Идентификацию клиента и trusted-proxy/IP policy.
- Ограничение частоты запросов и запросов по IP к публичным обработчикам, в том числе выдачи и замены.
- Идемпотентность и транзакции защищаемого действия после `Accepted`.
- Начальный жизненный цикл session и доступный альтернативный путь.

`Policy::maxActive*` ограничивает ёмкость состояния жизненного цикла, а не частоту запросов. Генерация выполняется до проверки этой ёмкости, поэтому её нельзя использовать как защиту от частых запросов к renderer.

## Ограничения визуальной CAPTCHA

TextImage и IconSequence — дополнительные барьеры в защите приложения. Пакет не гарантирует устойчивости к любым моделям или средствам автоматического распознавания. CAPTCHA также не подтверждает полномочия пользователя и не заменяет защиту прикладного действия.

Визуальные задания создают барьер для части пользователей. Приложение предоставляет [доступный альтернативный путь](accessibility.md), согласованный с защитой действия.
