# Жизненный цикл challenge

## Policy

Передайте `Policy` в `ChallengeService`. Значения по умолчанию:

| Поле | Значение | Назначение |
| --- | --- | --- |
| `ttlSeconds` | `180` | Срок действия нового задания |
| `maxWrongAttempts` | `3` | Предел неверных ответов |
| `maxActive` | `12` | Предел активных заданий в одном bucket |
| `maxActivePerPurpose` | `4` | Предел активных заданий одного назначения |
| `maxTombstones` | `32` | Предел сохраняемых терминальных записей |
| `terminalRetentionSeconds` | `180` | Период хранения терминальной записи |

Все значения положительны; лимит одного назначения не превышает общий. `maxActive*` — контроль ёмкости состояния, а не ограничение частоты HTTP-запросов.

## Issue

`issue($purpose, $kind)` выбирает зарегистрированную стратегию и готовит proof и представление до изменения storage. По умолчанию kind — `ChallengeKind::TextImage`.

В атомарной операции выполняется очистка состояния и проверка ёмкости. Новое задание сохраняется только при наличии места. Успех возвращает `LifecycleCode::Issued` и `IssuedChallenge`, отказ по ёмкости — `CapacityExceeded` без задания.

Новое задание получает серверные ID, purpose, kind, срок `expiresAt` и нулевой счётчик неверных ответов. Сбой подготовки не изменяет storage.

## Verify

`verify($id, $purpose, $submittedAnswer)` разрешает ID и серверное назначение в одной атомарной операции. Для активного задания стратегия определяется по kind в сохранённой записи, затем проверяется ответ и фиксируется итоговый переход.

Если состояние уже завершено, ответа стратегии не требуется: возвращается соответствующий `VerificationCode`. Некорректный формат пользовательского ответа является обычным отрицательным ответом для активного задания.

Срок проверяется и при итоговом переходе. Если он истёк за время проверки ответа, принятие не происходит. HTTP-статусы и тексты результата выбирает приложение.

## Неверные ответы

Обычный неверный ответ увеличивает серверный счётчик ошибок. До предела сервис возвращает `VerificationCode::Incorrect`. Срок действия задания от неверного ответа не продлевается.

Ответ, достигающий `maxWrongAttempts`, завершает задание и возвращает `AttemptsExhausted`. При настройках по умолчанию третий неверный ответ терминальный. Пока запись сохранена, последующие обращения возвращают тот же терминальный результат; `replace()` такого задания не выдаёт замену. Для продолжения используйте новую выдачу.

## Успешная проверка и replay

Принятый ответ потребляет задание в том же атомарном изменении состояния. Публичный результат — `VerificationCode::Accepted`.

Повтор при сохранённой терминальной записи возвращает `AlreadyConsumed`. После удаления записи старый ID возвращает `NotFound`, который также не разрешает действие. Проверка остаётся одноразовой, но причина отказа не хранится бессрочно.

Защищаемое действие выполняет приложение после `Accepted`. Атомарность состояния пакета не объединяет автоматически это действие со storage: транзакции и идемпотентность принадлежат приложению.

## Replace

`replace($oldId, $purpose, $kind)` сначала генерирует и отрисовывает замену, затем выполняет изменение жизненного цикла. По умолчанию новый kind — TextImage, независимо от типа старого задания; для других типов укажите его явно.

Заменяемым может быть активное задание либо сохранённая истёкшая запись с тем же purpose. Успех делает старый ID терминальным `Replaced`, выдаёт новый ID и возвращает `LifecycleCode::Refreshed` с новым заданием.

Замена активного задания нейтральна по числу активных записей и проходит даже на границе лимитов. Замена сохранённого истёкшего задания добавляет активную запись и может требовать свободной ёмкости. При `CapacityExceeded` новое задание не выдаётся.

Потреблённое, заменённое или исчерпавшее попытки задание не заменяется. После удаления записи старый ID возвращает `NotFound`. Неуспешная генерация или отрисовка замены не уничтожает старое задание.

При успешной замене приложение удаляет старый ответ и выбранные токены и показывает новые ID и Presentation.

## Expiry

`expiresAt` определяет действительность: задание активно только пока `now < expiresAt`. При `now >= expiresAt` очистка преобразует активную запись в истёкшую терминальную запись.

Очистка выполняется при операциях жизненного цикла. Наступление времени само по себе не запускает фоновую задачу, однако истёкшее задание больше не может дать `Accepted`.

Истёкшая запись может некоторое время сохраняться. Пока она сохранена, `verify()` различает `Expired`, а `replace()` обрабатывает её по правилам замены. После удаления записи старый ID возвращает `NotFound`.

## Retained state и pruning

Терминальные записи хранят причину завершения и ограничены временем и `maxTombstones`. Для истечения срока временная граница — `expiresAt + terminalRetentionSeconds`. Для потребления, исчерпания попыток и замены текущая граница — `max(исходный expiresAt, время завершения) + terminalRetentionSeconds`.

По достижении границы хранения очистка удаляет запись. При превышении `maxTombstones` старые записи могут быть удалены раньше; лимит выбирает более ранний `terminalAt`, при равенстве — меньший канонический ID.

Сохранённая истёкшая запись может допускать замену; после удаления записи старый ID возвращает `NotFound`. Произвольно старый истёкший ID нельзя бессрочно отличать от отсутствующего. Период хранения также не является гарантированным минимальным сроком: действует ограничение количества записей.

## Purpose mismatch

Если purpose не совпадает с назначением доступной записи, возвращается `PurposeMismatch`. Это отказ, а не успешная проверка или основание раскрыть браузеру детали состояния.

Такой переход не изменяет состояние пакета и не фиксирует побочную очистку. Если запись уже удалена, результат будет `NotFound`. Авторитетный purpose выбирает сервер для конкретного действия.

## Capacity

`maxActive` и `maxActivePerPurpose` ограничивают активное серверное состояние одного bucket. Поставляемый session adapter хранит его в области session. При заполнении лимита новая выдача не вытесняет действующие задания соседних вкладок.

Очистка истёкших заданий освобождает активную ёмкость; терминальные записи ограничены отдельно. Подготовка стратегии выполняется до проверки ёмкости, поэтому эти лимиты не ограничивают частоту запросов или стоимость повторной генерации. Request/IP throttling обеспечивает приложение.

## Коды результатов

| Операция | Успех | Обычные отрицательные результаты |
| --- | --- | --- |
| `issue()` → `IssueResult` | `Issued` + задание | `CapacityExceeded` |
| `replace()` → `IssueResult` | `Refreshed` + задание | `CapacityExceeded`, `NotFound`, `PurposeMismatch`, `AttemptsExhausted`, `AlreadyConsumed`, `Replaced` |
| `verify()` → `VerificationCode` | `Accepted` | `Incorrect`, `AttemptsExhausted`, `NotFound`, `PurposeMismatch`, `Expired`, `AlreadyConsumed`, `Replaced` |

В `IssueResult` отрицательный результат не содержит задания. Допустимые сочетания DTO, enum values и исключения приведены в [API](api.md).

## Гарантии и границы

Подготовка представления отделена от изменения storage. Проверка ответа, учёт ошибок и потребление выполняются внутри атомарного контракта `ChallengeStore`. При ошибке фиксации успешный результат не возвращается.

Гарантии adapter ограничены его поддерживаемым storage и окружением блокировок. Native session имеет собственный контракт фиксации и закрытия, описанный в [интеграции](../guides/integration.md).

Жизненный цикл не выполняет авторизацию, HTTP rate limiting или транзакцию защищаемого действия. [Модель безопасности](../security-model.md) описывает эту границу ответственности.
